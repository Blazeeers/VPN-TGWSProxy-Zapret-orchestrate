# omavpn-guard — надзиратель за обходами

`omavpn-guard` следит, чтобы **YouTube, Discord и Telegram работали**, а не
просто «были настроены». Он не подменяет `zapret-autotune`, а страхует его:
путь выбирает автотюн, а сторож проверяет результат и вмешивается, когда
результата нет.

## Кто за что отвечает

| Компонент | Роль |
|---|---|
| `zapret-autotune` (root, таймер) | **арбитр пути.** Подбирает стратегию DPI-обхода, держит `direct_domains.txt`, решает по каждой сети: работает обход (YouTube/Discord мимо VPN) или нужен VPN |
| `omavpn` | клиент VPN |
| `tg-ws-proxy` | локальный MTProto-прокси для Telegram |
| `omavpn-guard` (этот скрипт) | **надзор.** Проверяет сервисы, поднимает упавший VPN, чинит профиль, перезапускает прокси, перебирает ноды, просит автотюн перепровериться |

Важно: **VPN включён постоянно** — он нужен для остальных заблокированных
сайтов. Сторож его никогда не выключает. Меняется только путь YouTube, Discord
и Telegram: пока обход справляется — они идут мимо VPN, в VPN уходят лишь при
отказе обхода.

## Что и как проверяется

| Сервис | Проверка | Порог |
|---|---|---|
| YouTube | страница с содержимым, превью `i.ytimg.com`, `youtubei.googleapis.com` (служебный API плеера), медиа-CDN `googlevideo` | 200 + `image/*` >2 КБ + любой HTTP-ответ (не `000`) + 204/200 |
| Discord | `discord.com/api/v9/gateway` и сайт | 200 |
| Telegram | юнит `tg-ws-proxy`, `api.telegram.org`, `web.telegram.org` | active, 200/302, 200 |

Каждая проверка с повтором: одиночный транзиентный обрыв не считается поломкой
(на живой сети одиночный запрос падает примерно в 15 % случаев).

## Лечение

Порядок — от мягкого к жёсткому, каждый шаг проверяется:

1. **Telegram** — перезапуск юнита `tg-ws-proxy` (VPN для этого не нужен).
2. **`omavpn heal`** — собственное лечение клиента (перезапуск, перебор серверов).
3. **Перепрос стратегий** — сторож просит `zapret-autotune` проверить обход
   заново (файл `~/.cache/zapret-autotune/rescan.request`, ожидание по
   обновлению `.lastscan`, до 10 минут). Если запрос сгорел на занятом локе —
   повторяет его.
4. **Перебор нод** — до пяти живых серверов подписки, с возвратом прежней ноды,
   если ни одна не подошла.
5. **Крайняя мера** — сломанный сервис уходит в VPN (правка `direct_domains.txt`,
   атомарная запись, бэкап рядом). Не чаще раза в 15 минут и не больше трёх раз
   в час: если автотюн и сторож начнут тянуть файл в разные стороны, сторож
   отступает и пишет об этом в лог.

## Чем guard отличается от аудита маршрутов

Рядом работают два независимых механизма — они не дублируют друг друга:

| | `omavpn-guard` | аудит маршрутов (`bypass-status --route-audit`) |
|---|---|---|
| Что проверяет | сервисы целиком: YouTube (страница, превью, `youtubei` — только при поднятом туннеле, `googlevideo`), Discord, Telegram | только путь конкретного домена: отвечает ли он «как есть» и отвечает ли через VPN |
| Что лечит | перезапуск `tg-ws-proxy`, `omavpn heal`, перепрос стратегий zapret, перебор нод, в крайнем случае — `direct_domains.txt` | ставит оверрайд `~/.config/omavpn/route_overrides.json` (`omavpn route set … proxy`) |
| Чего не делает | не выключает VPN, не трогает оверрайды | не вызывает `omavpn heal`, не перебирает ноды, не правит `direct_domains.txt` |
| Частота | каждые 10 минут | каждые 10 минут + перепроверка оверрайдов раз в сутки |
| Файл | `~/.local/state/omavpn-guard/guard.log` | `~/.cache/<cli>/route-audit.json`, журнал systemd |

Порядок по «мягкости»: сначала guard пытается вылечить обход (zapret, ноды),
а аудит в это время просто возвращает домен на работающий путь: пробы всех
доменов, затем пачка оверрайдов без перезапуска и **один** `omavpn restart` на
весь прогон — без бэкоффов и без перебора нод. Если guard правит
`direct_domains.txt`, оверрайды аудита остаются в силе: они сильнее.

Подробности аудита — [route-audit.md](route-audit.md).

## Защита от «мигания»

- кулдаун 15 минут на ручную смену пути;
- не больше трёх переключений в час;
- экспоненциальный бэкофф после трёх неудач подряд (15 → 30 → 60 минут);
- счётчик неудач сбрасывается при смене сети — прошлые проблемы к новой сети
  не относятся;
- если `zapret-autotune` писал `direct_domains.txt` меньше минуты назад,
  сторож в файл не лезет;
- блокировка `flock`: два прогона одновременно не идут.

## Режимы

```bash
omavpn-guard              # проверка и лечение (это запускает таймер)
omavpn-guard --autostart  # поднять VPN при входе, если он был включён
omavpn-guard --status     # короткий JSON для отладки, без блокировки
```

`--status` печатает, например:

```json
{"tun_up":true,"intent":"on","path":"direct","autotune":"11","zapret":true,
 "caps_ok":true,"streak":0,"broken":""}
```

`broken` пуст — всё работает. `intent` — намерение пользователя: `on` (VPN
должен быть включён) или `off` (выключен вручную, сторож уважает выбор).

Служебный API `youtubei.googleapis.com` проверяется **только при поднятом
туннеле** (`tun_up`): он в `ALWAYS_PROXY_DOMAINS` и напрямую недоступен по
определению. Иначе при выключенном VPN и в режиме `mode proxy` (без TUN) сторож
считал бы YouTube сломанным каждые 10 минут, зря запускал перебор zapret под
root и включал VPN.

Проверка картинок YouTube больше не зависит от конкретного видео: вместо
превью `dQw4w9WgXcQ` — `generate_204` на самом `i.ytimg.com` плюс
`favicon.ico` (должен прийти `image/*`).

## Юниты

| Юнит | Что делает |
|---|---|
| `omavpn-guard.service` | один прогон проверки (`Type=oneshot`, `SuccessExitStatus=1`, `KillMode=process` — иначе systemd гасит поднятый VPN вместе с юнитом) |
| `omavpn-guard.timer` | запуск через 2 минуты после загрузки и каждые 10 минут после завершения предыдущего |
| `omavpn-autostart.service` | поднимает VPN при входе, если он был включён |

## Файлы

| Путь | Назначение |
|---|---|
| `~/.local/bin/omavpn-guard` | сам сторож |
| `~/.local/state/omavpn-guard/guard.log` | журнал (обрезается до 400 строк) |
| `~/.local/state/omavpn-guard/intent` | намерение пользователя: `on` / `off` |
| `~/.local/state/omavpn-guard/fail_streak`, `next_try` | бэкофф |
| `~/.local/state/omavpn-guard/switch_history` | история переключений пути |
| `~/.local/state/omavpn-guard/last_notify` | антидубль уведомлений |

## Зависимости

`bash`, `curl`, `jq`, `ip` (iproute2), `flock` (util-linux), `getcap` (libcap),
`systemd`, `NetworkManager` (`nmcli`), опционально `notify-send`.

Права `cap_net_admin` на `sing-box` выдаёт `install.sh` — без них сторож не
сможет поднять VPN и сообщит об этом.

## Если ничего не помогает

Сторож после трёх неудач подряд уходит в паузу и присылает уведомление. Что
смотреть:

```bash
tail -40 ~/.local/state/omavpn-guard/guard.log
omavpn-guard --status
omavpn --json status | python3 -m json.tool | head -20
tail -40 /var/log/zapret-autotune.log
systemctl --user list-timers omavpn-guard.timer
```

### Живость VPN в разных режимах

`vpn_alive()` учитывает режим: в `tun` нужен интерфейс `omavpn0`, в `proxy` — живой
xray и `running: true` в состоянии. Раньше проверялся только интерфейс, из-за чего в
режиме `proxy` сторож каждые 10 минут «поднимал» уже работающий VPN (фактически
перезапускал его) и слал ложные уведомления. Поле `mode` и `vpn_alive` есть в
`omavpn-guard --status`.
