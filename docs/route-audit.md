# Аудит маршрутов

Блокировки меняются: сегодня недоступен один служебный домен, через месяц —
другой CDN или API. Аудит маршрутов находит домен, который **не отвечает по
своему текущему пути**, и сам переводит его на рабочий — без человека.

Аудит **двусторонний**: он смотрит не только «из direct в туннель», но и
обратно.

Пример из жизни (22.10.2026, первое направление): YouTube «тормозил».
`www.youtube.com` отдавал 200, видео с `googlevideo.com` качалось 10–24 МБ/с, а
страница висела. Виноват был служебный API `youtubei.googleapis.com`: напрямую
все его адреса дают таймаут 10 с, а zapret его не пробивает — домена нет в
`/opt/zapret/ipset/zapret-hosts-user.txt`. Через VPN тот же домен отвечает за
1–2 с. Такую поломку не видно ни по «пингу», ни по открытию сайта.

Пример второго направления (в ночь на 22.10.2026): `zapret-autotune` перевёл
сеть в режим `vpn`, и **весь** видеотрафик `googlevideo.com` ушёл в туннель, где
он не работает — видео отдавало `code=000`, а страница при этом открывалась
(200). Аудит «только direct → proxy» такого не увидел бы: домен формально
«ходит через VPN», значит и лечить нечего. Теперь при провале на пути `proxy`
домен проверяется напрямую и, если там работает, возвращается в direct.

## Приоритет маршрутов

Правила собирает `bin/omavpn`, функция `build_singbox()`. Порядок правил —
это и есть приоритет:

```
1. override из ~/.config/omavpn/route_overrides.json  → proxy
2. ALWAYS_PROXY_DOMAINS                               → proxy
3. ALWAYS_DIRECT_DOMAINS + direct_domains.txt + оверрайды direct → direct
4. всё остальное                                      → final = proxy
```

Правило proxy стоит **перед** правилом direct, поэтому домен из пункта 1–2
физически не может попасть в direct.

### Почему overrides важнее direct_domains.txt

`~/.config/omavpn/direct_domains.txt` перезаписывает `zapret-autotune`
(root-таймер, раз в 30 минут). Это его рабочий инструмент: не справляется
обход в этой сети — он выкидывает домен из файла, и тот идёт через VPN.
Доверять этому файлу как источнику истины нельзя: любое решение автотюна
основано на стратегии zapret, а не на реальной доступности конкретного API.
Оверрайд — ручное (или автоматическое, от аудита) решение, которое автотюн
переписать не может: файл его не касается.

Если `route_overrides.json` нет — всё работает как раньше (кроме доменов из
`ALWAYS_PROXY_DOMAINS`, они идут в туннель всегда).

## Что проверяется

`ROUTE_PROBES` в `bin/bypass-status`:

| Домен | Проверка | Успех |
|---|---|---|
| `www.youtube.com` | `GET https://www.youtube.com/` | 200 и в теле есть `youtube` |
| `youtubei.googleapis.com` | `GET /youtubei/v1/player` | **любой** HTTP-код (405/400 — норма: TLS и ответ состоялись), `000`/таймаут — провал |
| `i.ytimg.com` | `GET /generate_204` | 204 или 200 (DNS + TLS + ответ CDN превью) |
| `redirector.googlevideo.com` | `GET /generate_204` | 204 или 200 |
| `discord.com` | `GET /api/v9/gateway` | 200 |
| `api.telegram.org` | `GET /` | 200 или 302 |
| `api.deepseek.com` | `GET /` | любой ответ ниже 500 (на 22.10.2026 — 401, это норма) |

Домены с «мягким» успехом (любой HTTP-код) выбраны намеренно: у служебных API
ответ 4xx — признак живой связи, а не поломки.

Проба `i.ytimg.com` раньше тянула превью конкретного видео (`dQw4w9WgXcQ`) —
плохая идея: удалят видео, и аудит вместе с guard будут считать CDN сломанным
по кругу. `generate_204` от содержимого не зависит и проверяет то же самое.

## Как проходит аудит

`bypass-status --route-audit` работает в три фазы — сначала смотрит, потом
меняет, потом проверяет.

**Фаза 1 — пробы (ничего не меняем).** Для каждого домена:

1. определяет текущий путь — по тем же правилам, что и sing-box: сначала
   спрашивает `omavpn --json route list` (единая логика приоритета, без
   дублирования), при старом CLI — читает правила из `singbox.json`;
2. проверяет домен «как есть» — `curl` идёт по текущему маршруту через TUN;
   провал подтверждается второй попыткой (одиночный обрыв на живой сети — не
   повод менять маршрут);
3. путь `direct` и провал — проверяет через VPN:
   `curl --socks5-hostname 127.0.0.1:<порт>`, порт берётся из `inbounds`
   `~/.local/state/<cli>/xray.json` (не хардкодится). Отвечает — домен идёт в
   очередь на переключение в `proxy`; не отвечает — «недоступен обоими путями»,
   не переключаем (дело не в маршруте);
4. путь `proxy` (или `default`, то есть `final=proxy`) и провал — домен идёт в
   очередь на **обратное** переключение в `direct`;
5. если плохо обоими путями — не переключает вообще.

**Фаза 2 — direct → proxy.** Все оверрайды ставятся пачкой с `--no-restart`,
затем **один** `omavpn restart` на всю пачку, пауза 2 с и перепроверка каждой
пробы. `verdict: "fixed"` ставится только если после переключения проба
реально прошла.

**Фаза 3 — proxy → direct.** То же для второго направления: пачка
`route set <домен> direct --reason "аудит: proxy не отвечает" --no-restart`,
один рестарт, пауза, перепроверка. Не помогло и там — оверрайд снимается
(`route unset`) либо возвращается прежний, и домен попадает в
«не отвечают: …». Итог — не больше двух переключений на домен за прогон
(туда и обратно).

Почему перезапуск один на пачку: `omavpn restart` пересобирает конфиг и
перезапускает xray + sing-box. Делать это семь раз подряд — значит семь раз
оборвать живой трафик и растянуть прогон на минуты.

### Чего аудит не делает

- не вызывает `omavpn heal`, не перебирает ноды, не трогает настройки VPN;
- не правит `direct_domains.txt` (это инструмент `zapret-autotune`);
- **не уводит в туннель домены из `ALWAYS_DIRECT_DOMAINS`** (`max.ru`,
  `deepseek.com`, `yandex*`, `tailscale*`): им нужен российский IP, через
  зарубежный выход они не работают. В detail пишется «помечен «только
  напрямую» — не переключаю»;
- **не выпускает напрямую домены из `ALWAYS_PROXY_DOMAINS`**
  (`youtubei.googleapis.com`, `youtube.googleapis.com`): напрямую они
  недоступны по определению, и «лечение» тут только навредит. Detail —
  «помечен «только через VPN» — в direct не перевожу»;
- **не трогает ручные оверрайды**: если у домена оверрайд с причиной не
  начинающейся с «аудит», значит его поставил человек — аудит уходит с
  пометкой «ручной оверрайд — не трогаю».

Списки «всегда» берутся из самого CLI (`omavpn --json route list` отдаёт
`always_direct` и `always_proxy`), поэтому аудит и конфиг не могут разойтись.

Выход — JSON:

```json
{"ok": true, "checked": 1792645769, "verdict": "fixed",
 "summary": "проверено 7, исправлено 1", "count": 7, "fixed": 1,
 "probes": [{"domain": "youtubei.googleapis.com", "path": "proxy",
             "before": true, "after": true, "action": "", "detail": "HTTP 405 · 2.4 с"}],
 "actions": [{"domain": "example.com", "from": "direct", "to": "proxy",
              "reason": "аудит: direct не отвечает"}],
 "secs": 8.4}
```

Кэш — `~/.cache/<cli>/route-audit.json` (его читает виджет: строка «маршруты:
проверено N, исправлено M» / «маршруты в порядке»). Журнал — systemd:
`journalctl --user -u omavpn-route-audit.service -n 50`.

## Перепроверка (раз в сутки)

`bypass-status --route-audit-recheck` берёт **свои** оверрайды `proxy` старше
24 часов (`reason` начинается с «аудит»; ручные не трогает никогда) и:

1. снимает их пачкой (`omavpn route unset --no-restart`), затем один
   перезапуск sing-box;
2. проверяет каждый домен напрямую;
3. работает — оверрайд остаётся снятым (блокировку убрали или zapret научился);
4. не работает — оверрайд возвращается с причиной «аудит: direct всё ещё не
   отвечает», и снова один перезапуск на всю пачку возвращённых.

Сам прогон тоже имеет ограничение: не чаще раза в 20 часов (страховка от
ручных запусков). Кэш — `~/.cache/<cli>/route-audit-recheck.json`.

## Лок и блокировки

- **Аудит и перепроверка** держат `flock` на
  `~/.cache/bypass-status/route-audit.lock`. Второй прогон не ждёт, а сразу
  отвечает `{"reason": "already_running"}`. Именно `flock`, а не файл с pid и
  mtime: при прогоне дольше «срока устаревания» второй процесс забирал лок, а
  потом `finally` первого снимал уже чужой — и два аудита начинали спорить за
  маршруты.
- **Все действия, меняющие живой VPN** (`on`, `off`, `restart`, `route
  set/unset`), берут неблокирующий `flock` на `~/.local/state/omavpn/ctrl.lock`.
  Рестартеров теперь четверо — таймеры аудита, перепроверка, guard и кнопки
  виджета — и без общего mutex два `on` одновременно сносят друг другу
  процессы. Занято — внятная ошибка «другой процесс управляет VPN».

## Оптимизации

- `omavpn route set` идемпотентна: если домен уже идёт этим путём, файл не
  переписывается и VPN не перезапускается. Это позволяет аудиту ставить
  десяток правил подряд и перезапускать один раз.

## Вручную

```bash
omavpn route list                     # таблица: домен, путь, источник, возраст, причина
omavpn route list --json              # то же в JSON (его читает bypass-status)
omavpn --json route list              # равноценная запись, как у остальных команд
omavpn route set example.com proxy --reason "API не отвечает напрямую"
omavpn route set example.com direct   # принудительно напрямую
omavpn route unset example.com        # вернуть обычный приоритет
omavpn route set example.com proxy --no-restart   # без перезапуска VPN

bypass-status --route-audit           # прогнать аудит вручную
bypass-status --route-audit-recheck   # перепроверить старые оверрайды
```

Источник в `route list`: `override` (файл оверрайдов), `always` (константы
`ALWAYS_PROXY_DOMAINS` / `ALWAYS_DIRECT_DOMAINS`), `file` (`direct_domains.txt`),
`default` (встроенный список), `final` (ни одно правило не сработало).

Путь в таблице считается **проходом по правилам в их порядке** — так же, как
это сделает sing-box. Поэтому `sub.youtubei.googleapis.com` показывается как
`proxy`/`always`, даже если он записан в `direct_domains.txt`: правило proxy
стоит первым и ловит поддомен по суффиксу. Раньше таблица смотрела только
точные совпадения и могла разойтись с конфигом.

`route set` проверяет домен после нормализации (нижний регистр, без точки на
конце): нужен обычный DNS-хвост. Шаблоны (`*.googleapis.com`), IP-адреса,
`localhost`, `x.com#comment`, пустые метки (`a..b`) и кириллица отклоняются с
внятным сообщением — sing-box сопоставляет `domain_suffix`, и «почти домен»
молча не сработал бы.

## Если файл оверрайдов повреждён

`route_overrides.json` пишется атомарно (временный файл + `os.replace`), поэтому
«полузаписанного» состояния практически не бывает. Но если файл всё же побит
руками или диском:

- `omavpn` печатает предупреждение в stderr и считает список **пустым** —
  маршруты работают по умолчанию, VPN не ломается;
- первая же запись (`route set`/`route unset`, аудит) перезапишет файл целиком.

Файл не секретный — там только домены, пути и причины.

## Откат

```bash
omavpn route unset youtubei.googleapis.com   # один домен
rm ~/.config/omavpn/route_overrides.json     # все оверрайды сразу
```

После отката домен снова подчиняется `direct_domains.txt`/умолчаниям. Если
это `ALWAYS_PROXY_DOMAINS`, он всё равно останется в туннеле — эти домены
заданы в коде намеренно (напрямую недоступны).

Полный откат вместе с автоматикой:

```bash
systemctl --user disable --now omavpn-route-audit.timer omavpn-route-recheck.timer
```

`uninstall.sh` (даже без `--purge`) удаляет `~/.config/omavpn/route_overrides.json`
и кэш `~/.cache/omavpn/route-audit*.json`: оверрайды — состояние машины, и
оставленные после переустановки они тихо уводят домены по правилам, которые
ставил аудит под другую сеть.

## Юниты

| Юнит | Когда |
|---|---|
| `omavpn-route-audit.service` | один прогон `bypass-status --route-audit` (`Type=oneshot`, `KillMode=process`) |
| `omavpn-route-audit.timer` | через 3 минуты после загрузки, дальше каждые 10 минут после завершения предыдущего |
| `omavpn-route-recheck.service` | один прогон `bypass-status --route-audit-recheck` (`KillMode=process`) |
| `omavpn-route-recheck.timer` | раз в сутки (через 12 минут после загрузки) |

Проверить:

```bash
systemctl --user list-timers 'omavpn-route-*'
systemctl --user status omavpn-route-audit.service
```

`KillMode=process` в юнитах — не украшение. Аудит вызывает
`omavpn route set` → `cmd_on()`, а тот запускает xray и sing-box с
`start_new_session=True`; процессы остаются в cgroup юнита, и systemd по
завершении oneshot-юнита убивает их вместе с собой (по умолчанию
`KillMode=control-group`). Итог без этой строки: VPN ложится после каждого
исправленного маршрута. Проверено экспериментом: `setsid`-ребёнок oneshot-юнита
с `KillMode=process` выживает, без неё — умирает.

## Ограничения

- Только IPv4 (`curl -4`) — как и весь проект: IPv6 в туннеле заблокирован.
- Проба идёт «как есть», поэтому при выключенном VPN путь `direct` — это
  настоящий прямой путь, а `proxy`-пробы упираются в мёртвый SOCKS. Аудит в
  таком состоянии ничего не переключает (проверка через VPN недоступна), в том
  числе не трогает второе направление: без живого SOCKS не понять, виноват
  маршрут или выключенный туннель.
- Если домен не отвечает ни напрямую, ни через VPN (VPN упал, сеть лежит),
  аудит молчит: лечением VPN занимается `omavpn-guard` (`docs/guard.md`).
- Таймаут одной пробы — 10 с; прогон по семи доменам занимает 10–30 с. Если
  менять пришлось в двух направлениях, рестартов будет больше одного (по одному
  на пачку и один на откат) — это осознанно: проверить второй путь без
  перезапуска нельзя.
